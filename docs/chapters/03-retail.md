# 03 日本語小売サポートを理解する

## 現在地
モデルより先に、何が正しい業務行動かを読みます。

## 目的
日本語化済みの小売デモを使い、自然な説明と正しい状態変更を同時に評価できるようにします。プロンプトやツールを再翻訳して別の実験にしません。

## 前提
元デモは[TracesDistillation](https://github.com/microsoft-foundry/fine-tuning/tree/main/Demos/TracesDistillation)です。新リポジトリに収録された日本語contract・ツール定義・架空業務コードを正本とし、上流の最新版と同一だと仮定しません。個別の移植元・変更は出典記録を参照します。

## 実施内容
正本は`src\foundry_distillation_lab\retail\contract\zava_system_prompt.md`と`zava_tools.json`です。6ツールの契約は次のようにつながります。完全な引数定義はJSONを読み、説明から推測して新設しません。

| ツール | 役割と次の処理への証拠 |
|---|---|
| `get_order_details` | 最初に注文の商品・会員・支払方法等を取得 |
| `get_fulfillment_status` | 商品ごとの配送・配達・遅延情報を取得 |
| `check_resolution_policy` | 対象商品ごとに理由と対応可否を確認し`policy_id`を返す |
| `check_inventory` | 交換の場合にSKU在庫を確認し`inventory_check_id`を返す |
| `calculate_resolution` | 確認IDを検証して返金・手数料・差額等を計算し`calculation_id`を返す |
| `submit_resolution` | 計算IDに対応する内容を日本語概要とともにシミュレーションとして確定 |

交換しない場合に在庫確認を常に追加する必要はありません。一方、計算なしで確定したり、確認IDを生成して埋めたりしてはいけません。確定処理は架空業務の状態を扱い、実店舗のシステムを変更しません。

次に、一つの顧客入力「届いた商品の返品を相談したい」を例に、何が不足しているかを判定します。識別情報が足りなければ確認質問で終了するのが正解になり得ます。注文・対象商品・期間等が確認でき、必要な条件を満たす場合だけ対応処理へ進みます。存在しない注文や未確認の商品を操作してはいけません。

| 境界 | 独立した期待の置き方 |
|---|---|
| 期間の境界 | 期限当日と翌日の期待を、実装の戻り値のコピーでなく仕様から決める |
| 対象の曖昧さ | 商品を勝手に選ばず、必要な確認で停止する |
| 前提手順の欠落 | 最終応答が自然でも、不正順序の操作は合格にしない |
| 不正要求の拒否 | ツールが防御した事実とモデルが不正要求した事実を別々に記録 |
| 正しい完了 | 確認IDや状態を捏造せず、観測した結果に基づいて説明する |

教材の仮想業務日は**2026-08-31**です。実行日の時計で期限を変えません。各ケースの状態を初期化し、別会話の処理結果が漏れないようにします。

## 出力
6ツールの役割表、代表的な正常・境界・不足情報ケース、contractとデータのversion/hashを残します。評価oracleや正解ファイルをagentの配置payloadへ含めません。

## 解釈
teacherの行動をすべて再現することと、業務上の成功は別です。必要な手順と正しい状態・説明が成立すれば、無意味な寄り道まで一致させる必要はありません。

## 完了条件
一つの顧客入力から複数のモデル/ツール呼び出しが生じる理由と、確認質問で止める理由を説明できます。

## 限界
これは架空データです。実顧客情報や実店舗への書込みは対象外です。顧客が質問に答える反復対話や顧客シミュレーターは実装範囲に含めません。
