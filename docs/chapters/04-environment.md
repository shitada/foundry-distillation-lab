# 04 環境・実験条件・安全な停止

## 現在地
オフライン実行環境と実験計画を準備します。Azureのリソース作成や推論を始める段階ではありません。

## 目的
第1章で挙げた検討項目、第2章の評価の考え方、第3章の業務内容を基に、実行環境・比較条件・判断基準を準備します。支出・再送・削除を制御する手順も揃えます。

## 前提
Windows / PowerShell、Python 3.13で確認する構成です。パッケージ宣言は3.11以上ですが、全版の確認済みという意味ではありません。初期インストールにはパッケージ取得の通信が生じ得ます。

## 実施内容

### 実行環境を用意する

リポジトリのルートで次を実行します。PowerShellの実行ポリシーを緩めず、仮想環境のPythonを直接指定できます。

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e .
.\.venv\Scripts\python.exe -m unittest discover -s tests
.\.venv\Scripts\python.exe scripts\collect.py --help
.\.venv\Scripts\python.exe scripts\train.py --help
.\.venv\Scripts\python.exe scripts\deployment.py --help
```

以降の章にある`python`は、この仮想環境のPythonを指します。リポジトリのルートで、コマンド先頭の`python`を`.\.venv\Scripts\python.exe`に置き換えて実行してください。仮想環境の有効化は不要です。

### 実験条件と判断基準を準備する

第1章で紹介した実験目標のメモを、具体的な実行・比較の条件へ落とし込みます。第2章の評価の考え方を使って、何を比較し、どの結果なら採用・見送り・保留とするかを記録します。

ここで作るのは評価結果ではなく、**同じ基準で結果を集め、判断するための実験計画と成績表のひな型**です。評価の条件と実行上の予算・停止条件を別々の場所で食い違わせず、同じ計画の中で管理します。

| 決める項目 | 記録する内容 |
|---|---|
| 実験の問い | 学習効果を知りたいのか、教師モデルの置き換えを判断したいのか |
| 比較対象と実行環境 | 教師モデル・学習前後の生徒モデルと各モデルの版。サブスクリプション、プロジェクト、リージョン、配置先、料金区分 |
| 共通の業務条件 | 業務ルール、指示文、ツール仕様、業務日、ケースと初期状態。使用する仕様の識別値 |
| 評価範囲と入力 | 問い合わせの種類、件数、繰り返す回数、実行順。ケースの版、入力ファイルの識別値 |
| 品質の基準 | 必須の確認、許される対応、重大な違反、成功の定義 |
| 許容する差 | 教師モデルと比べ、どの指標でどこまでの差を許容するか |
| 運用条件 | 許容待ち時間、想定する利用量・期間、必要な運用環境 |
| 学習・評価への投資 | 期待する効果、追加学習をする理由、データ生成・学習・評価に投資する予算。小規模試行と本実験の上限を分ける |
| 推論の予算と上限 | 教師モデル・学習前後の生徒モデル別の件数、時間、処理する文章量（トークン数）の上限、最大呼び出し回数、回復のための予備費 |
| 固定費と保持時間 | モデルの稼働、エージェント基盤、ツール・ログ・保存領域等の費用と保持時間 |
| 採用後の費用条件 | 実測に基づく運用費と、今後必要になる追加導入費の比較条件 |
| 停止・保留・照合 | 費用・時間の上限、障害や証拠不足が起きた場合の扱い、送信前の記録、成否不明時の照合、再送禁止条件 |
| 確認方法 | 自動で確かめる項目、人が読む項目、確認担当者 |
| データ管理 | 各データの用途、最終評価用データの保管先と管理者 |
| 所有リソース | この実験で作成した資源と、既存資源を区別した一覧 |
| 実行の承認 | 対象・入力・予算・期限・実行者に結び付けた明示的な承認 |

この時点ですべてを埋める必要はありません。数字や対象をまだ決められない項目は「未定」とし、**誰が、どの情報を基に、どの操作の前に確定するか**を記録します。教材の設定例や数値を、そのまま自分の業務で承認済みの条件として使わないでください。

第5章以降でデータや実行環境を確認しながら、同じ計画へ情報を補います。入力ファイルや業務仕様の内容を識別する値（ハッシュ値）も、対象が確定した段階で記録します。各実験の対象・入力・設定・予算は実行前に固定し、品質の合格基準や許容差は本評価の結果を見る前に決めます。結果に合わせて都合よく条件を書き換えてはいけません。

**計画の作成と、有料操作の承認は別です。** 実行に必要な項目が未定なら、その操作へ進みません。推論・学習・配置などの操作ごとに、確定した対象と入力、件数、見積り、予算、期限を確認して明示的な承認を得ます。最終的な採用判断の書き方は、第9章で扱います。

### 実行経路と、まだ確認できていない点を区別する

オフライン検証とネットワークpreflightを区別します。認証はSDKに合うDefaultAzureCredentialを基本にし、APIキーを教材やログへ保存しません。Preview経路、モデル利用可否、quota、SDK majorは実行前に公式資料と照合します。コントロール側とHosted Agentの依存を無理に一環境へ統合しません。

具体的なoperation、承認入力・対象、SDK分離と未検証点は[クラウド実行境界](https://github.com/shitada/foundry-distillation-lab/blob/main/docs/reference/cloud-execution.md)を確認します。Hosted skeletonのprotocol、コンテナー、SDKの内部HTTP hook、永続volume、identityは未検証です。現設計のjournal/予算は分散lockではないため、追試でも**永続書込先と単一replica**が必要です。ARMの条件付き更新/削除headerのサービス上の保証も未検証で、確認前の共有資源実行はブロック対象です。

将来の`collect.py --invoke`が起動するazdにも独立した検証が必要です。wrapperの一回起動と、azd内部のHTTP送信回数は同じ保証ではありません。SDK側のretry無効化をazdにも適用済みと誤認せず、拡張のflags・raw出力・内部retryを確認してから別承認へ進みます。

## 出力
実験計画と成績表のひな型、Python/SDK版、設定hash、承認の所在、所有資源一覧、停止・cleanup手順を非公開runへ保存します。計画には確定した条件だけでなく、未定の項目、その確認担当者と確定する段階も残します。

## 解釈
計画を記入したことは、モデルの品質や採用可否を確認したことではありません。また、SDK importや`--help`の成功は認証・配置・課金停止の確認ではありません。ローカル監視の期限切れでクラウドの学習やhostingが自動停止するとは限りません。

## 完了条件
無資格情報でオフラインテストが動き、比較条件・判断基準・予算・停止条件を管理する計画が用意できています。未定の項目について、確認担当者と確定する段階が明確であり、その操作の前に未定を解消すること、有料処理には別承認が必要であることを説明できます。cleanupはrunが所有すると証明できる対象だけに限定し、既存teacherを削除しません。

## 限界
本版ではクラウド通し実行は未検証です。live確認でSDKや契約を修正するときは、版を記録して新しいrunを開始し、途中の条件をすり替えません。
