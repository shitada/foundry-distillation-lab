# 実験条件・承認・停止の境界

## オフラインと有料実行

データの整形、保存済み結果の採点、仮想図表の生成にクラウド資格情報は不要です。
SDKや依存packageのダウンロードは環境準備の通信であり、モデル評価とは別です。
ネットワークを使う状態照会と、通信なしの検証を同じ「preflight」として混同しません。

有料操作の承認例は `configs/examples/approval.json` です。既定では無効です。
`approved` の明示的な真値、正確なoperation、対象、入力ファイルのSHA-256、
タイムゾーン付き期限、リクエスト数上限、通貨・費用上限を揃えてから実行します。
スクリプトが参照する別ファイルも、実行用requestに内容またはhashを固定します。
実行対象、ファイル、価格、パラメーターの変更は新しい承認を必要とします。

## 成否不明時に再送しない

送信前にattemptを排他的に保存します。結果が保存される前に停止した場合、
送信済みかどうか不明なので同じattemptを再送できません。
既存結果も上書きしません。新しいattempt IDを付ければ安全に再送できる、
という意味ではありません。元の要求のサービス側状態を読み取りで照合し、
未解決の支出を含めて再承認します。

`Approval.reserve` は承認ファイルと同じフォルダーの `.approval-state` に
呼び出し数と費用予約を保存します。同じ承認を読み直しても予約はリセットされません。
この保守的な予約を実請求額として足し込んではいけません。
予約は自動で返却せず、usageや請求が不明なら未確定のまま停止します。
不明なlockやpendingファイルを削除して続行する手順は標準化しません。

承認・journalは協調的なローカル実行の誤操作防止です。
ファイルを改変できる利用者に対する認可境界ではなく、
Azureの課金上限やサービス側のリトライ停止を保証するものでもありません。
保持時間やSDK timeoutを過ぎたから無料になったとはみなしません。

## データ・条件を変更したら

環境の修復でも、モデル入力、業務処理、採点、依存関係による挙動が変わったか確認します。
期待値・許容差を都合よく変えて既存結果を合格にしません。
変更した条件の新旧versionを残し、比較可能性を判断します。
最終評価を見て改善した場合は新たな独立最終評価が必要です。

## 後片付け

そのrunが作ったと確認できるリソースをmanifestに記録します。
削除前に所有対象・課金への影響・保持する証跡を確認して明示的に実行します。
元のteacher、既存モデル、学習原本を一括削除しません。
削除要求の受付と、サービス上での不在確認、課金の確定はそれぞれ別の状態です。
